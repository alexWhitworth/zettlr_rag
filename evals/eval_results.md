## Evaluation Results

### My Corpus Stats:

It is important to note that my library is quite limited in size and scope. This places an upper 
bound on output quality and many topics have no coverage at all. RAG will obviously not work if 
there is no retrieval.

- Documents: ~700
- Chunks available for retrieval: ~4600

```
├── business_and_industry  # ~40 docs
├── causal_inference       # ~110
├── data_methods           # ~40
├── digital_privacy        # ~75
├── economics              # ~100
├── experimentation        # ~50
├── llm                    # ~50
├── ml_engineering         # ~5 (longer files)
├── ml_methods             # ~125
├── software_eng           # ~2
└── statistics             # ~100
```

To evaluate answer quality, I implemented LLM-as-a-Judge using a diverse set of 75 questions 
generated by Claude Sonnet 4.6 utilizing only the folder names in the corpus. RAG answers were 
compared to [Consensus AI](https://consensus.app/) and the associated citations returned by
Consensus.

### **tl;dr:**

Across the key dimensions we see the following:
1. **Low cost:** roughly 1/2 cent per query (~10k tokens), with input tokens as 95% of total 
tokens.
2. **Acceptable Latency:** ~15-20 sec/query, driven by `LLMRerank`; but latency still compares 
favorably to Consensus AI
3. **High Answer Reliability:** $R \approxeq 0.98$, $CD \approxeq 0.2$, $H_{\text{sem}} = 0$.
4. **Answer Quality:** Given the limited corpus, quite reasonable -- across the 75 evaluation
questions, we judge 34 as equal quality and 41 as worse quality. 
   
### Answer Quality Details

Overall, we see that the RAG system works well, conditional on corpus availability. **That is, 
when the RAG finds content in the corpus, it generates answers consistent with the Consensus AI 
benchmark.** More precisely, the system is precision-OK and recall-poor. Further, precision and 
recall are highly correlated ($\hat \rho = 0.8$). 

A retrieval ablation study further demonstrates that performance limitations are due to corpus 
constraints. And, lastly, we see that retrieval depth is only moderately correlated with both 
precision and recall. This is the canonical fingerprint of a corpus bottlenecked system, 
consistent with the corpus only having ~700 docs.

- **Precision:** `mean(factual_precision) = 0.71`: Most claims are supported; minor unsupported 
asides.
- **Recall:** `mean(content_recall) = 0.45`: About half of key points covered; major omissions 
remain.
- **Retrieval quality:** mean of `7.3` out of `10.0` with (p10, p90) of `(5.7, 9.0)`. 
- **Fluence and structure:** mean of `0.85` indicating well structured, polished, and clear responses.

### Conclusions

1. **Would I implement this sytem in production?**

**No.** The current design has very high indexing costs due to using Claude Opus to summarize each
paper. This is not scalable.

But, for my use case, the summarization SKILL serves two purposes. Firstly, it helps me increase
paper reading velocity given sizeable time constraints. By reading the summary first, which
is more detailed than the abstract, I can determine which papers to read closely. Secondly,
the paper summaries are useful themselves when reviewing my notes.

2. **What would I implement?**

I'd compare two options, giving a reasonable comparison to SF-RAG, referenced below, but without
requring building a custom paper tree implementation.

```
| **Stage**       | **Option A** | **Option B** |

| **Retrieval**   | Vector + BM25 | Vector + BM25 |
| **Fusion**      | Reciprocal rank | Reciprocal rank |
```
